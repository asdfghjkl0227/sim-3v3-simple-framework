## 根因、修正和验收

| 问题 | 已定位的代码原因 | 当前修正 | 验收场景 |
| --- | --- | --- | --- |
| 门前不行动 | 普通场内余量限制；SDK 绕到球后时，机器人稍过门线就取消任务；快球太早交给慢速 SDK 追球 | 允许门柱之间短距离站到门线后继续救险；快球先走预测拦截点；禁区内优先解围，失败后短换位 | 门线后 0.2 m 仍解围；快球先迎球；暂停/对方重启仍中止 |
| 边线不抢 | 场内钳制和踢球位置闸门相互叠加，不能从球外侧回踢 | 球员可在边线外最多约 0.4 m 范围短绕行，目标向中路，球仍按官方状态处理 | 上下两条边线、外侧姿态向场内踢球、重启限制不被绕过 |
| 前场不争 | 保护点用 `min(-3.8, ball.x - 5.2)`，始终留在深后场 | 保护者跟随球前移；落后压得更高，任何球员都可成为争球者 | 球在对方半场时，基点也能进入对方半场 |
| 接不住传球 | 接球人按普通支援避球；传球后还可能重新建立传球计划、双方继续抢同一球；固定 2 s 窗口过短 | 专门的迎球动作，不绕球；接球角色锁定，传球者前插；窗口按球速和路程计算 | 传球离脚后只有接球人迎球，接球后才重新分工 |
| 准备站位太深 | 只投影到最近合法位置，原来在球门旁就继续待在那里 | 三个准备点为约 (-2.4,0)、(-0.8,±2.3)，按总行走距离分配 | READY 全员在本方、中圈外，两个点靠中场 |
| 防守无人负责 | 原有区域点无法覆盖三名对手；第一版纯盯人又把最后保护者带离射门通道 | 对方持球时一对一分配，第一人占球门侧并争抢；球进入本方半场，最后保护者优先守射门通道，盯人归属仍保留 | 对手不重复指派；本方半场至少一人补球门；前场不固定留门将 |
| 蹲坑过早 | 原来领先一球且临近结束也会收缩 | 仅净胜至少 2 球时收缩；落后为 chase，其余 balanced | 比分差 -2/0/1/2/3，剩余 1 s 也不改变阈值 |

## 奖励账本

| 事件 | 分值 | 记录依据 |
| --- | --- | --- |
| 接住队友传球 | +0.2 | 已观测传球离脚，指定接球人形成持续近球优势，估计事件 |
| 失去球权 / 未接住 | -0.2 | 持球优势消失超过观察窗口；或传球超时、被对方获得、官方死球；一次传球只结算一次 |
| 断球 | +0.3 | 持续观测到对方控制转为我方控制，估计事件 |
| 被断球 | -0.3 | 我方控制直接转为对方控制；同时失去球权 -0.2，合计 -0.5 |
| 边线球救回 | +0.3 | 边线踢球请求后，球重新进入内场至少 1 m，估计事件 |
| 禁区内解围 | +0.6 | 禁区内踢球请求后，球实际离开本方禁区并有足够位移；发命令本身不得分 |
| 犯规被罚下 | -0.5 | 官方 penalty 从无变为罚下 |
| 进球 | +1 | 官方我方比分增加 |

模块为 `src/evaluation.py`，日志为 `EVAL event=... value=... total=... evidence=...`，内存中最多保留 200 个事件。其他观测、传球与球路日志仍保留。奖励用于日志评估和传球风险排序；当前是明确规则的策略，不是完成训练的强化学习模型，不会因为简单加分就自动学会动作。

第一版日志确实出现估算 `intercept`、`loss`、`dispossessed`、`penalty_area_clearance` 和 `missed_pass`；例如本机 00:23:21 的禁区解围 +0.6，00:31:09 的 missed_pass -0.2（总分 -2.7）。尚未确认实际传球接住或边线救回成功，不能把测试用例当作实赛成功次数。

## 第二版针对失败的修正

- READY 先走最近合法点，再走中场准备阵型，避免从对方半场/界外直接追远端阵型点。
- 最后保护者在本方半场补门，防止盯远端人导致空门。
- 快球距球员超过 0.65 m 时先迎预测点，不立即交给 SDK 慢走绕球；慢球再进入持续踢球。
- 门线后仅门柱之间允许救险所需站位；暂停、罚下和对方重启闸门优先。
- 普通远射距离从 8 m 缩至 5.5 m，增加中场传给接应者的机会。
- 62 项假后端场景测试通过；编译与 diff 空白检查通过。实际动作效果以第二轮比赛为准。

第二轮进一步观察：我方 00:25 球门球直到 01:10 超时才开放；07:49 画面中三名我方队员均挤向同侧。代码另查出：传球接球人较远时允许第三人成为处理者，而后又给指定接球人下迎球指令，形成双人迎球；旧 receiver 球权也可能过早终止新传球计划。第三版锁定唯一接球者、要求当前近球慢球条件才结束接球计划；本方半场的最后保护者不再依赖持球估计，仍允许前场前压和最近者出击；己方重启改用相同的活球接近路径，出球仍经过重启闸门。

第二轮日志尾部可见本机 00:49:49 `receive +0.20 player=1 evidence=estimated`，00:50:00 估算累计 -5.50。它说明接球估计器触发过，不足以证明真实接球质量；尤其本轮已发现旧 owner 提前结束计划的问题，不能用这个数代替逐次录像核验。

“接住/控制/断球”用公开位置估计，不是真实触球身份。边线救回目前按“在边线把球踢回内场”计，不能可靠追溯更早是哪一方把球踢到边线。短时间争抢、双方同距、观测丢失都可能漏记或误判；这些估计不用于解除裁判限制。

## 规则与风险

## R5 / R6 新证据（2026-11-18）

R5 完整终场 1:2。07:40 我方进球；对方 00:58、02:30 进球。05:14 robot1、08:22 robot2 非法站位。04:11、05:24、08:55 三次我方角球均 45 秒超时，06:39 卡球坠球。连续大败由 4 归零，没有触发用户要求的连续 5 场净负至少 3 球重建条件。

R6 对这场证据修复：球门保护角色改为不避球、近身解围；我方开球接应保持中场两翼；定位球接应跟随球的位置；角球球门外侧增加底线短绕行空间。69 项离线回归通过，运行日志 tid 26746。实赛仍在进行，不能当作改善成功。

R6 开场又暴露恢复故障：00:20 robot2、00:29 robot3 因倒地未恢复罚下，00:50、00:59 解除。01:50 左右本机运行日志反复出现 get_up task already running；随后 AUDIT 显示两名球员返场位置约 (-5,5)、(-6,5) 长期 switching_mode。代码 `_recovering` 只在 fall_down_state 为 normal 且 mode 已为 walk 时清除，但该标记本身又阻止请求 walk，存在恢复完成后模式循环等待。应以明确的 normal 状态解除恢复等待，然后请求模式；None / getting_up 不可提前放行。待本场完整结束后修改验证。

战术目标改为争球、接应、解围和进球；不再为普通活球无活动预防而退到距球 3.6 m 外。SET / stopped、官方罚下及对方重启仍有动作闸门，避免无意义的少人和失效进球；新版 G-03 距离条件继续保留。

边线外绕行是用户明确选择的比赛风险：仅处理可踢活球的球员允许短距离越边线，其他队员和 READY 仍在场内。SDK 持续踢球会自行移动，策略不能保证它不把球踢出界、也不能保证边线越界不被处罚。

`src/framework/` 保持不改，策略只用官方 Context。暂停时不新启动起身，SDK 已执行的不可取消起身任务仍有原有限制。

## R9–R11 实赛事实与第十一版修复
